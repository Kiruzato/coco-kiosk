Design and implement a new Administrative Management UI for CoCo.
Do NOT reuse or modify the old flat directory UI.
Build a new Admin interface specifically aligned with the current CQE schema and architecture.
________________________________________
Core Requirements
1️⃣ Entity Separation (Structured Navigation)
The Admin UI must separate entity types into distinct sections, similar to browser tabs or a sidebar navigation.
Each entity must have its own dedicated section:
•	Campus
•	Building
•	Floor
•	Room
•	OutdoorLocation
•	Department
Do NOT mix all entities in a single generic list.
Navigation between these sections must be clear and intuitive.
________________________________________
2️⃣ Entity-Specific Add Panels
Each entity type must have its own structured “Add” panel.
Do NOT use a single generic add form for all entities.
When clicking “Add” inside a section:
•	Show a panel or modal specific to that entity type.
•	Only show fields relevant to that entity.
Examples:
•	Room → show building dropdown, floor dropdown, primary type dropdown, tags input.
•	Floor → show building dropdown, level_number input, display name.
•	OutdoorLocation → no building/floor fields.
________________________________________
3️⃣ Structured Fields Must Use Dropdowns
For all relational or categorical fields, use dropdown selectors:
•	Campus selection
•	Building selection
•	Floor selection
•	Department selection
•	Primary type selection (CLASSROOM, OFFICE, RESTROOM, OTHER)
Do NOT allow free-text input for structured relationships.
________________________________________
4️⃣ Tag Support
Room and OutdoorLocation must support tag creation and management:
•	Admin can add multiple tags.
•	Tags must be normalized (lowercase, trimmed, no duplicates).
•	Tag input should support adding/removing dynamically.
•	Existing tags may be suggested if feasible.
________________________________________
5️⃣ Filtering and Sorting
Each entity section must support:
•	Search by name
•	Filter by status (ACTIVE / INACTIVE)
•	Sorting (at minimum by name)
For Room section, also support:
•	Filter by campus
•	Filter by building
•	Filter by primary type
Filtering must be lightweight and responsive.
________________________________________
6️⃣ Hard Delete Support
Room and OutdoorLocation must support hard delete.
Hard delete must:
•	Require explicit confirmation.
•	Permanently remove the entity.
•	Trigger CQE index rebuild after deletion.
•	Update UI accordingly.
Do NOT implement cascade delete for higher-level entities.
________________________________________
7️⃣ CQE Integration
After any create, update, or delete operation:
•	Persist changes to JSON.
•	Trigger safe CQE index rebuild.
•	Ensure deterministic behavior remains intact.
Do not modify CQE logic unless strictly necessary.
________________________________________
8️⃣ Design Principles
•	Keep the UI clean and structured.
•	Avoid unnecessary complexity.
•	Do not over-engineer.
•	Prioritize clarity and maintainability.
•	Align strictly with the current schema.
•	Ensure compatibility with Raspberry Pi 5 deployment.
________________________________________
Deliverables
Provide:
•	Admin UI architecture design
•	Component breakdown
•	Data flow explanation
•	CRUD implementation strategy
•	CQE integration strategy
•	Validation flow
•	Hard delete implementation plan
Do not redesign the schema.
Do not expand into intelligence features.
Focus strictly on building a proper, structured Admin system for CQE.
