1. INGESTION PIPELINE OVERVIEW
================================================================================

The ingestion pipeline transforms raw documents into a searchable vector
database (FAISS index) that the CoCo chatbot uses for Retrieval-Augmented
Generation (RAG). The complete flow is:

  Input Documents (.txt, .pdf, .docx)
    |
    v
  Document Loading & Text Extraction
    |
    v
  Text Normalization Pipeline (PDF only, 5 stages)
    |
    v
  Chunking (layout-aware for PDFs, linear for TXT/DOCX)
    |
    v
  Consolidation Engine (synthetic chunk generation)
    |
    v
  Metadata Validation (Phase 23 schema checks)
    |
    v
  Embedding Generation (OpenAI text-embedding-3-small)
    |
    v
  FAISS Vector Index Creation
    |
    v
  Metadata Index Generation (O(1) lookups)
    |
    v
  RAG Package (vector_store/ + document_registry.json + .zip)

ENTRY POINTS:

  - CLI: python ingest.py <documents_folder>
  - GUI: python gui.py (tkinter desktop application)
  - Batch file: "CoCo Ingestion Module.bat" (Windows launcher)

The GUI provides an OpenAI API key input field, folder picker, progress bar,
and log panel. It calls the same run_ingestion() function as the CLI.


2. DOCUMENT PROCESSING
================================================================================

2.1 Supported File Types
-------------------------
  - .txt  (plain text)
  - .pdf  (Portable Document Format)
  - .docx (Microsoft Word)

File type detection is based on file extension (case-insensitive).
Files with other extensions are silently ignored during directory scanning.

2.2 How Documents Are Read and Parsed
--------------------------------------

TXT FILES:
  - Read with UTF-8 encoding using Python's open()
  - No preprocessing; raw text passed directly to chunking

PDF FILES (two parsing paths):
  Path A - Layout-Aware Parsing (preferred):
    - Uses unstructured.partition_pdf() with strategy="fast"
    - Extracts structured elements: Title, NarrativeText, ListItem, Table
    - Each element carries metadata (page_number, element type)
    - Table elements preserve HTML structure when available
    - Falls back to Path B if unstructured library is not installed or parsing fails

  Path B - Linear Extraction (fallback):
    - Uses pypdf (or PyPDF2) PdfReader
    - Extracts text page-by-page via page.extract_text()
    - Pages joined with double newline separators
    - No structural information preserved

DOCX FILES:
  - Uses python-docx library
  - Extracts paragraph text via doc.paragraphs
  - Empty paragraphs are filtered out
  - Paragraphs joined with double newline separators

2.3 Duplicate Detection
------------------------
Before ingestion, a SHA-256 hash of each file is computed (calculate_file_hash).
The hash is checked against the DocumentRegistry. If a matching hash exists and
skip_duplicates=True (default), the file is skipped with a "Duplicate" message.

2.4 Text Normalization (Pre-Chunking)
--------------------------------------
Two normalization layers exist:

LAYER 1 - Text Normalizer Pipeline (text_normalizer_pipeline.py)
  Applied ONLY to layout-aware PDF elements, BEFORE chunking.
  Five deterministic stages:

  Stage 1: Whitespace Normalization
    - CRLF -> LF
    - Collapse 3+ spaces to single space
    - Remove trailing whitespace per line
    - Collapse 2+ blank lines to single blank line

  Stage 2: Line Reassembly
    - Detects fragmented person entries (e.g., "Dr." on one line, name on next)
    - Merges title + name into single element when title is alone

  Stage 3: OCR Artifact Removal
    - Fixes known OCR typos: "CHARPERSON" -> "CHAIRPERSON", "Direcor" -> "Director"
    - Removes Unicode private use area characters (U+E000-U+F8FF)
    - Fixes spacing around periods in titles ("Asst ." -> "Asst.")
    - Normalizes Unicode to ASCII (NFKD decomposition)

  Stage 4: Person Entry Normalization
    - Standardizes title casing: "DR." -> "Dr.", "ENGR." -> "Engr."
    - Removes "& FACULTY" descriptors
    - Cleans parenthetical spacing: "( College" -> "(College"

  Stage 5: Entity Block Cleanup
    - Detects enumeration blocks (Deans, Directors, Chairpersons)
    - Removes interspersed noise headers (e.g., "Student Organizations")
    - Removes standalone role descriptors
    - Preserves only person entries within enumeration blocks

LAYER 2 - Text Normalizer (text_normalizer.py)
  Applied to ALL chunk text at embedding time:
    1. Unicode NFKC normalization
    2. Lowercase conversion
    3. Collapse all whitespace to single space
    4. Strip leading/trailing whitespace

  This ensures case-insensitive matching between queries and documents.
  Original text is preserved in chunk metadata["original_text"] for display.


3. CHUNKING STRATEGY
================================================================================

There are TWO distinct chunking strategies, selected based on file type
and library availability:

3.1 Layout-Aware Chunking (PDFs with unstructured library)
-----------------------------------------------------------

This is the PRIMARY chunking path for PDF files.

STEP 1: Element Extraction
  unstructured.partition_pdf() extracts structured elements:
  - Title, NarrativeText, ListItem, Table, etc.
  Each element has a type, text content, and page number.

STEP 2: Text Normalization Pipeline
  The 5-stage pipeline (described in Section 2.4) cleans PDF artifacts.

STEP 3: Section Grouping (group_elements_by_section)
  Elements are grouped into logical sections:
  - A "Title" element starts a new section
  - All subsequent non-Title elements belong to that section
  - Each section records: section_title, elements, element_types, page_numbers

  APPENDIX DETECTION (Phase 22):
    Sections with titles matching "Appendix [A-Z]" or known appendix items
    ("Columban Hymn", "Prayer to St. Columban") are flagged as appendix sections.
    Appendix sections are NEVER merged with other sections.

STEP 4: Administrative Section Merging (merge_related_admin_sections)
  Enumeration groups (Deans, Directors, VPs, Chairs) are detected and merged:
  - Title-only sections are merged with their following content sections
  - Sections on same/adjacent pages with same role type are consolidated
  - Elements are reordered: Titles first, then Person entries, then Other
  - Appendix sections are excluded from merging

STEP 5: Chunk Creation (create_chunks_from_sections)
  For each section:

  CASE 1: Section fits within max_size (800 chars, or 2000 for appendix)
    -> Kept as a single chunk

  CASE 2: Section exceeds max_size
    -> Split at ELEMENT BOUNDARIES (never mid-element)
    -> Elements are accumulated until adding the next would exceed max_size
    -> Current accumulated elements become one chunk
    -> Process continues with remaining elements

  KEY PARAMETERS:
    - target_size: 500 characters (default, configurable via CLI)
    - max_size: min(chunk_size * 2, 800) = 800 characters for normal sections
    - APPENDIX_MAX_SIZE: 2000 characters for appendix sections
    - NO OVERLAP between chunks in layout-aware mode

  IMPORTANT: Layout-aware chunking has NO OVERLAP between chunks.
  Chunks are split at element boundaries, not at character positions.

3.2 Linear Chunking (TXT, DOCX, and PDF fallback)
---------------------------------------------------

Uses LangChain's RecursiveCharacterTextSplitter.

  KEY PARAMETERS:
    - chunk_size: 500 characters (default, configurable)
    - chunk_overlap: 50 characters (default, configurable)
    - length_function: len (Python's built-in character count)
    - separators: ["\n\n", "\n", ". ", " ", ""]

  HOW IT WORKS:
  RecursiveCharacterTextSplitter tries to split text using separators in order
  of preference:

  1. First tries "\n\n" (paragraph boundaries)
  2. If chunks are still too large, tries "\n" (line boundaries)
  3. Then ". " (sentence boundaries)
  4. Then " " (word boundaries)
  5. Finally "" (character-level split, last resort)

  The splitter works recursively:
  - Split text using the first separator that produces chunks
  - If any resulting chunk exceeds chunk_size, recursively split it
    using the next separator in the list
  - Continue until all chunks are within chunk_size

  OVERLAP BEHAVIOR:
  - chunk_overlap=50 means the last 50 characters of chunk N are repeated
    at the beginning of chunk N+1
  - This preserves context across chunk boundaries
  - Overlap is applied AFTER splitting, by prepending characters from the
    end of the previous chunk

  UNIT OF MEASUREMENT:
  - All sizes are in CHARACTERS, not tokens
  - length_function=len uses Python's len(), which counts Unicode characters
  - A 500-character chunk is approximately 100-125 English tokens


4. CHUNK BOUNDARY RULES ("Early Chunk Cut-Off" Behavior)
================================================================================

4.1 Layout-Aware Mode (PDFs)
------------------------------

WHAT DETERMINES WHEN A CHUNK STOPS:
  - A chunk stops when adding the NEXT PDF element would exceed max_size (800 chars)
  - Chunks are NEVER cut mid-element
  - Splitting happens at element boundaries (between paragraphs, titles, list items)

EARLY TRUNCATION:
  - NO truncation occurs. Elements are kept intact.
  - If a single element exceeds max_size, it becomes its own chunk (possibly oversized)
  - There is no secondary splitting of oversized single elements in layout-aware mode

SENTENCE/PARAGRAPH ALIGNMENT:
  - Chunks naturally align with structural boundaries because they split at
    element boundaries (which correspond to paragraphs, titles, list items, etc.)
  - This means chunks will NEVER be cut mid-sentence in layout-aware mode

OVERLAP:
  - NO overlap exists between layout-aware chunks
  - Each element appears in exactly one chunk

4.2 Linear Mode (TXT, DOCX, PDF fallback)
-------------------------------------------

WHAT DETERMINES WHEN A CHUNK STOPS:
  - A chunk stops at 500 characters (default)
  - The splitter tries to find the best separator near the boundary

EARLY TRUNCATION:
  - The splitter prefers to cut at paragraph boundaries ("\n\n")
  - If no paragraph boundary exists within range, it tries line boundaries ("\n")
  - Then sentence boundaries (". ")
  - Then word boundaries (" ")
  - Only as a last resort does it cut mid-word ("")

CAN CHUNKS BE CUT MID-SENTENCE?
  - Yes, but only if a sentence exceeds 500 characters
  - The splitter first tries paragraph and line boundaries
  - For sentences under 500 characters, they will be kept intact
  - For very long sentences (>500 chars), the splitter falls through to
    word-level or character-level splitting

OVERLAP BEHAVIOR:
  - 50 characters from the end of chunk N are prepended to chunk N+1
  - This means the last ~10 words of each chunk are repeated in the next chunk
  - Overlap ensures that information near chunk boundaries is not lost

EXAMPLE:
  Given text: "Paragraph A (200 chars).\n\nParagraph B (400 chars).\n\nParagraph C (150 chars)."

  Chunk 1: "Paragraph A.\n\nParagraph B." (600 chars, exceeds 500)
  -> Splitter splits at "\n\n" boundary
  Chunk 1: "Paragraph A." (200 chars)
  Chunk 2: [50-char overlap from A] + "Paragraph B." (400 chars)
  Chunk 3: [50-char overlap from B] + "Paragraph C." (150 chars)


5. EMBEDDING GENERATION
================================================================================

5.1 Embedding Model
---------------------
  Model: OpenAI text-embedding-3-small
  Provider: OpenAI API (requires OPENAI_API_KEY)
  Library: langchain_openai.OpenAIEmbeddings

  The model is initialized once per DocumentManager instance:
    self.embeddings = OpenAIEmbeddings(openai_api_key=self.api_key)

  Default model dimensions: 1536 (text-embedding-3-small default)

5.2 How Embeddings Are Generated
----------------------------------
  - Each chunk's page_content (NORMALIZED text, lowercase) is sent to OpenAI
  - The API returns a 1536-dimensional float vector for each chunk
  - Embeddings are generated in batch by LangChain when calling:
      FAISS.from_documents(documents, self.embeddings)  # New store
      self.vector_store.add_documents(documents)         # Incremental

  IMPORTANT: Embeddings are generated from NORMALIZED text (lowercase, collapsed
  whitespace), NOT from the original text. This ensures that queries normalized
  the same way will have maximum cosine similarity with relevant chunks.

  The original (display-quality) text is preserved in metadata["original_text"]
  and used when presenting results to the user.

5.3 Cost Considerations
-------------------------
  text-embedding-3-small pricing: $0.02 per 1M tokens (as of 2024)
  A typical campus document set (4 documents, ~620 chunks) costs < $0.01 to embed.


6. VECTOR STORE CREATION
================================================================================

6.1 FAISS Index
-----------------
  Library: faiss-cpu (via langchain_community.vectorstores.FAISS)
  Index type: IndexFlatL2 (brute-force L2 distance, LangChain default)

  Creation:
    - First document: FAISS.from_documents(documents, embeddings)
      Creates a new FAISS index from scratch
    - Subsequent documents: vector_store.add_documents(documents)
      Adds new vectors incrementally to the existing index

  Storage files:
    - index.faiss: The FAISS index binary (vector data + index structure)
    - index.pkl: Python pickle of the LangChain docstore (Document objects,
      metadata, and the index_to_docstore_id mapping)

  The docstore maps FAISS integer indices to UUID-based docstore IDs,
  which in turn map to Document objects containing page_content and metadata.

6.2 Metadata Storage
----------------------
  Each chunk's metadata is stored in the LangChain docstore (index.pkl).
  Metadata fields per chunk:

  STANDARD FIELDS (all chunks):
    - document_id: MD5 hash identifier for the source document
    - document_name: Original filename (e.g., "handbook.pdf")
    - file_type: File extension (".pdf", ".txt", ".docx")
    - ingestion_timestamp: ISO format datetime of ingestion
    - chunk_id: Sequential integer within the document
    - total_chunks: Total number of chunks from this document
    - section: Extracted section name (legacy compatibility)
    - original_text: Original (non-normalized) text for display

  PDF LAYOUT-AWARE FIELDS (additional):
    - section_title: Explicit section heading from PDF structure
    - element_types: List of element types in this chunk (Title, NarrativeText, etc.)
    - page_numbers: Sorted list of page numbers spanned by this chunk
    - is_appendix: Boolean flag for appendix sections
    - appendix_id: Appendix identifier (A, B, C, etc.) or None

  SYNTHETIC CHUNK FIELDS (consolidation engine output):
    - is_synthetic: True
    - entity_type: Type of consolidated entity ("deans", "prayer")
    - source_chunk_ids: List of original chunk IDs that were consolidated
    - consolidation_phase: Phase that created this synthetic chunk
    - num_entities: Number of entities consolidated

6.3 Metadata Index (Phase 25)
-------------------------------
  After FAISS index creation, a MetadataIndex is built and saved to
  data/metadata_index.json. This provides O(1) lookups by:
    - chunk_id
    - section/section_title
    - page number
    - document_id

  This index is used at runtime for fast filtering (e.g., neighbor chunk
  expansion in Phase 19) without iterating the entire FAISS docstore.

6.4 Document Registry
-----------------------
  Stored as document_registry.json, tracking each ingested document:
    - document_name, file_type, file_hash (SHA-256)
    - file_path (absolute path to source file)
    - ingestion_timestamp
    - num_chunks, chunk_size, chunk_overlap

  Used for duplicate detection and document management operations.


7. RAG PACKAGE GENERATION
================================================================================

7.1 Package Structure
-----------------------
  The output package is created inside the documents folder with a timestamped
  name:

  <documents_folder>/
    rag_package_YYYY-MM-DD_HH-MM/
      vector_store/
        index.faiss          # FAISS vector index
        index.pkl            # LangChain docstore (metadata + mappings)
      document_registry.json # Document tracking metadata
    rag_package_YYYY-MM-DD_HH-MM.zip  # Compressed package

7.2 ZIP File Creation
-----------------------
  - Created using Python's zipfile.ZipFile with ZIP_DEFLATED compression
  - Contains:
      vector_store/index.faiss
      vector_store/index.pkl
      document_registry.json
  - Archive paths are relative (no absolute paths in ZIP)

7.3 Validation
----------------
  Before ZIP creation, the pipeline validates that all required files exist:
    - vector_store/index.faiss
    - vector_store/index.pkl
    - document_registry.json

  File sizes are logged. If any required file is missing, ingestion fails.

7.4 Deployment
----------------
  The ZIP file is designed for upload via:
    1. Admin UI > RAG Package (web upload at /admin#rag-package)
    2. Manual copy of vector_store/ directory to WEB_APP/modules/

  The runtime system (WEB_APP) loads the FAISS index at startup from
  WEB_APP/modules/vector_store/.

================================================================================
  SUMMARY
================================================================================

The CoCo ingestion pipeline processes documents through a sophisticated
multi-stage pipeline:

1. Documents are loaded based on file type (TXT, PDF, DOCX)
2. PDFs receive layout-aware parsing (unstructured library) that preserves
   document structure (titles, paragraphs, lists, tables)
3. PDF elements pass through a 5-stage text normalization pipeline to clean
   OCR artifacts and normalize formatting
4. Chunking is structure-aware for PDFs (splitting at element boundaries,
   max 800 chars) or character-based for other formats (500 chars, 50 overlap)
5. A consolidation engine creates synthetic chunks for enumeration groups
   (deans, prayer) to ensure complete retrieval
6. All chunk text is normalized (lowercase, whitespace collapsed) for embedding
7. OpenAI text-embedding-3-small generates 1536-dimensional vectors
8. FAISS stores vectors with full metadata in index.faiss + index.pkl
9. A metadata index enables O(1) lookups at runtime
10. Everything is packaged into a timestamped ZIP for deployment

KEY TECHNICAL FACTS FOR THESIS DEFENSE:
  - Chunk sizes are measured in CHARACTERS, not tokens (500 chars ~ 100-125 tokens)
  - PDF chunking splits at ELEMENT boundaries (never mid-paragraph)
  - Linear chunking prefers paragraph > line > sentence > word boundaries
  - Layout-aware chunks have NO overlap; linear chunks have 50-char overlap
  - Embeddings use NORMALIZED (lowercase) text; original text preserved in metadata
  - The consolidation engine creates synthetic "super-chunks" for entities like
    deans that may be scattered across multiple PDF pages
  - Appendix sections get a larger max_size (2000 chars vs 800) to stay intact
