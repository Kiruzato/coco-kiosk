Phase 17C: Single Retrieval Pipeline + Enumeration Stability
Phase 17A–17B stabilized retrieval correctness, grounding, routing, and answer presentation. However, list-style queries (e.g., “list all the deans”) still produce inconsistent or incomplete results due to:
•	Dual retrieval (validated chunks differ from LLM context)
•	Retrieval top-k being too low for enumeration
•	Chunk competition near the cutoff boundary
This phase eliminates context drift and ensures stable, complete enumeration answers.
________________________________________
Goals
•	Ensure the LLM uses exactly the same retrieved chunks that were hybrid-ranked and validated
•	Remove dual retrieval paths
•	Increase recall for list-style queries
•	Make enumeration responses deterministic and complete
________________________________________
Required Changes
1. Eliminate Dual Retrieval (Critical)
Currently:
•	Hybrid retrieval + grounding validation occurs
•	Then ConversationalRetrievalChain performs a SECOND retrieval with its own retriever
This must be removed.
Replace with:
•	Perform retrieval once (hybrid + validation)
•	Pass the validated chunks directly into the LLM prompt
Use:
•	StuffDocumentsChain, or
•	Direct LLM call with constructed context
The LLM must receive ONLY the already-scored, already-validated chunks.
No secondary retriever is allowed.
________________________________________
2. Increase Retrieval Top-K
Update:
RETRIEVAL_TOP_K = 4
To:
RETRIEVAL_TOP_K = 8
This ensures list-style queries (deans, awards, offices) can retrieve all relevant entities.
Latency impact is acceptable on RPI5 for this scale.
________________________________________
3. Preserve Existing Safety Guarantees
Must remain unchanged:
•	Hybrid scoring (0.7 vector / 0.3 keyword)
•	Grounding validation logic
•	Confidence thresholds
•	Directory routing
•	RAG-only mode behavior
This phase modifies retrieval flow only.
________________________________________
Implementation Guidance
•	Remove or bypass ConversationalRetrievalChain retriever usage
•	Replace with single retrieval pipeline:
query
→ hybrid retrieval (k=8)
→ re-ranking
→ grounding validation
→ pass validated chunks to LLM
→ structured answer builder
•	Ensure confidence scoring uses the SAME chunk set
•	Ensure LLM context uses the SAME chunk set
Add logging:
•	retrieval_chunks_used_count
•	enumeration_query_detected (optional heuristic: “list”, “all”, plural nouns)
________________________________________
Validation Criteria
The following queries must return COMPLETE and consistent results across runs:
•	“list all the deans”
•	“who are the deans”
•	“show all college deans”
Expected:
•	All 5 deans appear every time
•	Ordering may vary, but membership must be complete
•	No missing entities
•	Same result across repeated queries
________________________________________
Non-Goals
•	No chunk strategy changes
•	No answer formatting changes
•	No admin changes
•	No memory changes
Chunk restructuring may be addressed in a later phase only if necessary.
________________________________________
Outcome
After this phase:
•	Retrieval happens exactly once per query
•	LLM answers are grounded in the validated chunks
•	Enumeration queries become deterministic
•	All list entities are consistently returned
This completes core RAG correctness for campus knowledge.
