SECTION 1: HIGH-LEVEL ASSESSMENT
================================================================================

1.1 STRENGTHS
-------------
The current system demonstrates solid production-grade engineering:

- Retrieval-First Routing: Correctly prioritizes document retrieval before
  general AI fallback. This is the right pattern for factual Q&A.

- Hybrid Retrieval: The 70/30 vector/keyword split addresses semantic drift
  (e.g., "Dean's Lister" vs "Team Leadership Award"). Industry best practice.

- Deterministic Extraction: Using regex-based extraction for enumerations
  (deans, etc.) eliminates LLM hallucination risk for structured data.

- Synthetic Chunk Consolidation: Creating single authoritative chunks for
  scattered entities (deans, prayers) is a proven pattern from enterprise RAG.

- Grounding Validation: Requiring query terms in retrieved chunks prevents
  confident-but-wrong answers. The semantic override (Phase 20) correctly
  handles long-form content without weakening keyword grounding.

- Single Retrieval Pipeline: Passing the same validated chunks to LLM that
  were used for grounding ensures consistency. Many production systems fail here.

- Edge-Optimized: FAISS local persistence, session-scoped memory, and
  offline-first design are appropriate for Raspberry Pi deployment.

1.2 AREAS FOR IMPROVEMENT
-------------------------
- Chunking Fragility: Prayer split across 4 chunks indicates chunking
  strategy needs refinement for appendix/special content sections.

- Metadata Inconsistency: Chunks 648-650 labeled "General Information"
  instead of "Prayer to St. Columban" suggests section detection gaps.

- Reactive Consolidation: Synthetic chunks are created per-entity type
  (deans, prayers). This pattern does not scale to N entity types.

- Limited Evaluation Infrastructure: No automated regression suite for
  retrieval quality, grounding accuracy, or answer completeness.

- Single-Document Assumption: Current design optimized for one PDF.
  Multi-document corpus will require namespace/collection strategy.

SECTION 2: CONCRETE RECOMMENDATIONS (PRIORITIZED)
================================================================================

------------------------------------------------------------------------------
PRIORITY 1: CHUNKING AND INGESTION ROBUSTNESS (High Impact, Medium Effort)
------------------------------------------------------------------------------

Problem:
Long-form content (prayers, hymns, policies) gets fragmented across chunks
with incorrect section labels. Current fix (synthetic consolidation) is
reactive rather than preventive.

Recommendations:

A. Implement Section-Aware Chunk Boundaries

   Instead of fixed chunk_size=500, use adaptive chunking:

   - Detect section headers via layout analysis (already have element_types)
   - Never split within a detected section smaller than max_chunk_size
   - For large sections, split at paragraph boundaries (double newline)
   - Preserve section title in ALL child chunks

   Implementation:
   - Modify chunk_document() to accept section_boundaries parameter
   - Use element_types=['Title'] positions as hard boundaries
   - Add min_chunk_size threshold to prevent orphan fragments

B. Add Appendix/Special Section Handling

   Appendices (Hymn, Prayer, etc.) have different structure than body content.

   - Detect appendix markers ("Appendix A", "Appendix B", etc.)
   - Treat entire appendix section as single chunk if under 2000 chars
   - If over 2000 chars, split at logical boundaries (verse breaks, etc.)

   Implementation:
   - Add is_appendix flag to section metadata
   - Create appendix-specific chunking rules in chunk_document()

C. Section Label Propagation

   Ensure all chunks inherit correct section title from parent:

   - When splitting a section, propagate section_title to ALL fragments
   - Add parent_section_id to metadata for provenance tracking
   - Validate section labels post-chunking (no "General Information" orphans)

Tradeoff: Slightly larger chunks increase embedding cost but dramatically
improve retrieval coherence. For edge deployment, this is acceptable.

------------------------------------------------------------------------------
PRIORITY 2: GENERIC CONSOLIDATION FRAMEWORK (High Impact, Medium Effort)
------------------------------------------------------------------------------

Problem:
Current consolidation is hardcoded per entity type (consolidate_dean_chunks,
consolidate_prayer_chunks). Adding new entity types requires code changes.

Recommendations:

A. Create Declarative Consolidation Rules

   Define consolidation rules in configuration, not code:

   consolidation_rules.json:
   {
     "rules": [
       {
         "entity_type": "deans",
         "anchor_patterns": ["dean", "deans"],
         "required_patterns": ["dr.", "engr.", "arch.", "prof."],
         "exclude_patterns": ["dean's office", "is tasked"],
         "section_title": "Deans",
         "chunk_id": -1
       },
       {
         "entity_type": "prayer",
         "anchor_patterns": ["prayer to st. columban"],
         "continuation_patterns": ["o beloved columban", "through christ our lord"],
         "section_title": "Prayer to St. Columban",
         "chunk_id": -2
       }
     ]
   }

B. Implement Generic Consolidation Engine

   Single function that processes rules:

   def consolidate_by_rules(documents, rules_config):
       for rule in rules_config['rules']:
           documents = apply_consolidation_rule(documents, rule)
       return documents

   Benefits:
   - Add new entity types without code changes
   - Easier testing and validation
   - Non-engineers can extend consolidation

C. Auto-Detection Mode (Future)

   Analyze chunk graph to detect candidates for consolidation:
   - Adjacent chunks with same section prefix
   - Fragments under 100 chars
   - Chunks that form incomplete sentences

   Surface candidates for human review rather than auto-consolidating.

------------------------------------------------------------------------------
PRIORITY 3: METADATA STRATEGY (Medium Impact, Low Effort)
------------------------------------------------------------------------------

Problem:
Metadata is ad-hoc. Some chunks have page_numbers, some have element_types,
synthetic chunks have different fields than natural chunks.

Recommendations:

A. Define Canonical Metadata Schema

   All chunks MUST have:
   - chunk_id: int (unique, sequential for natural; negative for synthetic)
   - document_id: str (hash of source document)
   - document_name: str
   - section: str (never empty, never "General Information" as default)
   - section_title: str
   - page_numbers: List[int]
   - char_offset_start: int (position in source document)
   - char_offset_end: int
   - is_synthetic: bool (default False)
   - created_at: str (ISO timestamp)

   Optional fields:
   - entity_type: str (for synthetic chunks)
   - source_chunk_ids: List[int] (for synthetic chunks)
   - element_types: List[str] (from layout analysis)
   - parent_section_id: str (for split sections)

B. Validate Metadata at Ingestion

   Add metadata validation step after chunking:

   def validate_chunk_metadata(chunk):
       required = ['chunk_id', 'document_id', 'section', 'page_numbers']
       for field in required:
           if field not in chunk.metadata or chunk.metadata[field] is None:
               raise ValueError(f"Missing required metadata: {field}")
       if chunk.metadata['section'] == 'General Information':
           logger.warning(f"Chunk {chunk.metadata['chunk_id']} has default section")

C. Add Metadata Index

   For fast filtering without vector search:

   metadata_index.json:
   {
     "by_section": {"Deans": [62, 652, -1], "Prayer": [647, -2]},
     "by_document": {"manual.pdf": [0, 1, 2, ...]},
     "synthetic_chunks": [-1, -2],
     "page_index": {12: [60, 61, 62], 134: [645, 646, 647]}
   }

   Enables queries like "all chunks from page 12" without embedding search.

PRIORITY 4: EVALUATION AND OBSERVABILITY (High Impact, Medium Effort)
------------------------------------------------------------------------------

Problem:
No systematic way to detect regressions in retrieval quality, grounding
accuracy, or answer completeness. Current testing is manual.

Recommendations:

A. Create Golden Test Set

   Curate 50-100 test cases with expected outcomes:

   golden_tests.json:
   [
     {
       "id": "prayer_complete",
       "query": "Prayer to Saint Columban",
       "expected_mode": "campus",
       "must_contain": ["Help Us", "through Christ our Lord", "Amen"],
       "must_not_contain": ["I don't have"],
       "expected_chunk_ids": [-2],
       "min_confidence": "Medium"
     },
     {
       "id": "dean_count",
       "query": "Who are the deans",
       "expected_mode": "campus",
       "expected_entity_count": 6,
       "must_contain": ["Almazan", "Capili", "Matriano", "Yap", "Gonzales", "Gutierrez"]
     }
   ]

B. Implement Automated Regression Runner

   Run golden tests on every ingestion or code change:

   python scripts/run_golden_tests.py --report reports/regression.txt

   Output:
   - Pass/fail per test case
   - Retrieval metrics (chunks retrieved, scores)
   - Grounding metrics (terms matched, mode used)
   - Answer metrics (contains expected, length)

C. Add Retrieval Quality Metrics

   Track and log:
   - MRR (Mean Reciprocal Rank) for known-answer queries
   - Grounding success rate (% queries that pass grounding)
   - Confidence distribution (% High/Medium/Low)
   - Rejection rate (% queries refused)
   - Synthetic chunk hit rate (% queries using synthetic chunks)

D. Observability Dashboard Enhancement

   Current /admin/analytics tracks events. Extend to include:
   - Retrieval quality trends over time
   - Most common grounding failures
   - Queries with lowest confidence scores
   - Chunk utilization heatmap (which chunks are retrieved most)

PRIORITY 5: RETRIEVAL QUALITY IMPROVEMENTS (Medium Impact, Medium Effort)
------------------------------------------------------------------------------

A. Query Expansion for Synonyms

   Current system relies on exact term matching for keyword component.
   Add lightweight synonym expansion:

   synonyms = {
     "library": ["lib", "reading room", "book room"],
     "registrar": ["registration", "enrollment office"],
     "dean": ["deans", "college head"]
   }

   Expand query terms before keyword scoring. Keep synonym list small and
   domain-specific to avoid noise.

B. Implement Reciprocal Rank Fusion (RRF)

   Current hybrid: 0.7 * vector + 0.3 * keyword

   RRF is more robust to score distribution differences:

   def rrf_score(vector_rank, keyword_rank, k=60):
       return 1/(k + vector_rank) + 1/(k + keyword_rank)

   Re-rank by RRF score instead of weighted sum. Industry standard for
   hybrid retrieval (used by Elasticsearch, Pinecone).

C. Add Negative Examples to Grounding

   Current grounding checks if query terms appear in chunks.
   Add negative validation:

   - If query asks about "Dean's Lister" but top chunk is about "Deans",
     detect entity mismatch and refuse
   - Maintain confusion_pairs list: [("Dean's Lister", "Dean"), ...]

   Prevents semantic neighbor confusion more explicitly.

D. Chunk Diversity in Results

   Current: top-K by score
   Problem: May return 5 chunks from same section, missing other relevant content

   Add diversity constraint:
   - Limit max 2 chunks per section in top-K
   - Or use MMR (Maximal Marginal Relevance) for diverse retrieval

PRIORITY 6: DETERMINISM VS LLM BOUNDARIES (Low Effort, High Value)
------------------------------------------------------------------------------

Current system has good instincts here. Codify the rules:

A. Document Decision Matrix

   Create explicit rules for when to use deterministic vs LLM:

   DETERMINISTIC (no LLM):
   - Directory queries (entity resolution)
   - Enumeration extraction (deans, awards, etc.)
   - Simple lookups with exact matches
   - Disambiguation prompts

   LLM WITH GROUNDING:
   - Open-ended campus questions
   - Long-form content retrieval
   - Context synthesis from multiple chunks
   - Follow-up question interpretation

   LLM WITHOUT GROUNDING (general mode):
   - Greetings and small talk
   - Out-of-scope questions (explicit)
   - Meta questions about the chatbot

B. Add Deterministic Extractors for Common Patterns

   Beyond deans, add extractors for:
   - Awards and honors
   - Office hours
   - Contact information (phone, email patterns)
   - Dates and schedules

   Use regex + template responses, not LLM.

C. Confidence-Based Routing

   Formalize the routing logic:

   if confidence >= HIGH and is_deterministic_query:
       return deterministic_response()
   elif confidence >= MEDIUM and grounding_passed:
       return llm_with_context()
   elif confidence >= LOW and allow_general:
       return llm_general()
   else:
       return refusal_response()

------------------------------------------------------------------------------
PRIORITY 7: MULTI-DOCUMENT SCALABILITY (Medium Impact, Higher Effort)
------------------------------------------------------------------------------

Current system assumes single PDF. For multiple documents:

A. Document Namespace Strategy

   Add document isolation:
   - Each document gets unique document_id (content hash)
   - Chunk IDs scoped to document: {document_id}_{chunk_id}
   - Synthetic chunks also scoped: {document_id}_synthetic_{entity_type}

B. Collection-Based Organization

   Group related documents:

   collections = {
     "student_manual": ["2022_manual.pdf", "2023_addendum.pdf"],
     "faculty_handbook": ["faculty_guide.pdf"],
     "campus_directory": ["directory_entities.json"]
   }

   Route queries to appropriate collection based on intent.

C. Incremental Ingestion

   Current: Full re-ingestion on document update
   Better: Incremental updates

   - Track chunk hashes
   - On re-ingestion, only update changed chunks
   - Maintain version history for rollback

D. Cross-Document Retrieval

   For queries spanning multiple documents:
   - Retrieve from all collections
   - Merge and re-rank results
   - Indicate source document in response

------------------------------------------------------------------------------
PRIORITY 8: EDGE DEPLOYMENT OPTIMIZATIONS (Low Impact, Low Effort)
------------------------------------------------------------------------------

A. Memory Management

   - Lazy-load vector store (only when first query arrives)
   - Unload after idle timeout (e.g., 30 minutes)
   - Use memory-mapped FAISS index for large corpora

B. Embedding Cache

   - Cache embeddings for common queries
   - LRU cache with 1000 entry limit
   - Reduces API calls and latency

C. Response Caching

   - Cache full responses for exact query matches
   - Short TTL (5 minutes) to handle updates
   - Invalidate on document re-ingestion

D. Batch Embedding on Ingestion

   - Current: Embed chunks one by one
   - Better: Batch embed (50-100 at a time)
   - Reduces API overhead significantly

================================================================================
SECTION 5: CONCLUSION
================================================================================

The CoCo system demonstrates mature RAG engineering practices. The hybrid
retrieval, grounding validation, and deterministic extraction patterns are
production-grade. The main opportunities are:

1. PREVENTIVE over REACTIVE: Fix chunking at source rather than patching
   with synthetic consolidation for each edge case.

2. DECLARATIVE over IMPERATIVE: Move rules to configuration so non-engineers
   can extend the system.

3. MEASURABLE over ANECDOTAL: Implement golden tests and metrics to catch
   regressions before users do.

4. SCALABLE over SINGLE-USE: Design for multi-document corpus even if
   current deployment is single-document.

The system is well-positioned for these improvements given its clean
separation of concerns and phased development approach.
