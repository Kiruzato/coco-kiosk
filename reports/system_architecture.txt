System Overview
The CoCo Campus RAG Chatbot is a localized, retrieval-augmented generation system designed to provide deterministic and reliable information in a kiosk environment. The system processes natural language queries through a multi-stage pipeline that combines vector similarity search, keyword-based scoring, and structured entity resolution. Its primary architectural goal is to eliminate hallucination for factual queries (e.g., directory locations, office hours) while leveraging Large Language Model (LLM) capabilities for semantic synthesis of unstructured policy documents. The system supports both text and voice interactions, operating on an offline-first deployment model optimized for edge devices like the Raspberry Pi 5.

Architecture Layers

Ingestion Pipeline
The ingestion layer is responsible for transforming raw source documents into retrievable knowledge. It accepts PDF, DOCX, and TXT files and processes them through a multi-stage normalization pipeline. Key components include `document_manager.py`, which orchestrates the workflow, and `text_normalizer_pipeline.py`, which cleanses parsing artifacts (e.g., PDF headers, hyphens) to ensure data quality. A specialized consolidation engine (`consolidation_engine.py`) pre-aggregates related entities (such as lists of deans or prayers) into single "synthetic chunks" to guarantee complete retrieval. This layer ensures that the index contains high-quality, semantically coherent segments rather than raw, fragmented text.

Query Processing Pipeline
The core runtime engine handles user input and orchestrates the retrieval-generation loop. The main entry point is `app.py`, which implements a "retrieval-first" routing logic. Before invoking any generative model, the system attempts to ground the query in the document store using `retrieval_validator.py`. If sufficient evidence is found, the relevant chunks are passed to the `ChatOpenAI` model via LangChain. This layer also manages conversation history (`ConversationBufferWindowMemory`) and session state, ensuring context is preserved across multi-turn interactions.

Retrieval & Storage
This layer manages the vector index and keyword metadata. We utilize FAISS (Facebook AI Similarity Search) for efficient dense vector storage and retrieval. To address the limitations of pure vector search, we implement a hybrid retrieval strategy: vector similarity (weighted 0.7) is combined with BM25-style keyword coverage (weighted 0.3). Additionally, a `MetadataIndex` provides O(1) lookups for deterministic filtering. This dual approach ensures that queries match both conceptual meaning and specific terminology (e.g., acronyms, names).

Deterministic Extraction Layer
For high-stakes factual queries, the system bypasses the probabilistic LLM generation in favor of rule-based extraction. The `entity_registry.py` and `entity_extractor` modules manage structured data for building locations, office hours, and event dates. When an intent classifier (`intent_classifier.py`) detects a directory or schedule query, the system retrieves the answer directly from a JSON-backed registry or uses regex-based extraction from the source text. This guarantees 100% accuracy for wayfinding and contact information.

Voice Modality Layer
The voice infrastructure enables hands-free interaction for the kiosk. It is implemented as a modular service package (`voice/`) containing an orchestrator, a Speech-to-Text (STT) service using `whisper.cpp` (optimized for ARM64), and a Text-to-Speech (TTS) service using Piper. The orchestrator manages the audio I/O pipeline, handling format conversion and state transitions (e.g., listening, processing, speaking). This layer is designed to be offline-first, minimizing latency and external API dependencies.

Frontend & UI
The user interface is a lightweight, static web application served by FastAPI. It is designed specifically for touch-based kiosk interaction, featuring large controls and high-contrast visual feedback. The UI layer (`static/index.html`, `app.js`) manages the chat state, renders structured responses (not just plain text blocks), and visualizes the voice interaction state (e.g., pulsing mic button). It communicates with the backend via REST endpoints and WebSockets for real-time status updates.

Observability & Admin
To support production maintenance, the system includes a comprehensive observability suite. `event_tracker.py` and `query_logger.py` record interaction data, identifying failed retrievals and user refusals. An administrative dashboard (`admin.py`) allows non-technical staff to manage the document corpus, view analytics, and update entity records without modifying the codebase. This layer provides the feedback loop necessary for continuous content improvement.

Ingestion Pipeline Flow
1. PDF/DOCX Upload: Admin uploads files via the Admin UI.
2. Parsing & Normalization: Text is extracted and cleaned of artifacts (NFKC, whitespace).
3. Section & Entity Consolidation: Related segments (e.g., lists, appendices) are grouped into synthetic chunks.
4. Chunking: Text is split into uniform segments (e.g., 500 characters) if not already consolidated.
5. Embedding: Chunks are converted to vector embeddings using OpenAI's embedding model.
6. Indexing: embeddings are stored in the local FAISS index; metadata is saved to `document_registry.json`.

Query Pipeline Flow
1. User Query: Text input or transcribed voice audio.
2. Intent Classification: System checks if the query is a directory lookup or general chat.
3. Hybrid Retrieval:
   - Vector search retrieves top-k candidates.
   - Keyword scoring adjusts ranks based on term coverage.
   - Reciprocal Rank Fusion (RRF) combines scores.
4. Validation & Grounding:
   - System verifies if top chunks contain query terms (Keyword Grounding).
   - Or checks if high-similarity semantic match exists (Semantic Override).
5. Context Assembly: Valid chunks are selected; neighbors are expanded if needed.
6. Response Generation:
   - If deterministic: structured answer is pulled from registry.
   - If generative: LLM synthesizes answer using strict "answer only from context" prompt.
7. Output: JSON response with answer text, sources, and confidence score is sent to UI.

Deterministic Logic vs. LLM Usage
The system employs a strict separation of concerns. Deterministic logic is used for:
- "Where is..." (Location/Directory)
- "When is..." (Event Dates)
- "Who is the dean of..." (Enumeration Lists)
- Routing decisions (Campus vs. General)
The LLM is used exclusively for:
- Summarizing prose text (Policies, Mission Statements).
- Synthesizing natural language explanations from retrieved fact chunks.
- Handling conversational transitions.
This hybrid approach prevents the "hallucination of facts" common in pure generative systems.

Grounding + Confidence + Semantic Override
To ensuring reliability, every retrieval result undergoes a validation process. A "Grounding Check" typically requires that key terms from the query appear explicitly in the retrieved text. If this check fails, the retrieval is discarded. However, for conceptual queries (e.g., "Tell me a prayer"), a "Semantic Override" logic activates: if the vector similarity is very high (>0.75) and the text is long-form, the keyword requirement is bypassed. The system assigns a confidence score (High/Medium/Low) based on these factors, refusing to answer if confidence drops below a configured threshold (usually Medium).

Voice Integration
Voice is treated as an input/output modality wrapper around the core chat pipeline. When a user speaks, the audio is captured by the frontend and streamed to the `whisper.cpp` service for transcription. This text is then injected into the standard `handle_chat` pipeline as if it were typed. The text response from the chatbot is then sent to the TTS service (Piper) to generate an audio file, which is played back to the user. The `voice_orchestrator` ensures these steps happen synchronously, handling error states (e.g., silence detection) without blocking the main specific server threads.

Deployment Model
The architecture is containerized and designed for edge deployment on a Raspberry Pi 5. The vector store (FAISS) and document registry are local files, removing the need for an external database server. The voice services run locally to minimize latency. The application is served via Uvicorn/FastAPI, allowing it to function as a standalone appliance on the campus intranet without constant cloud connectivity (except for the periodic API calls to OpenAI for embeddings/generation).

Design Principles
1. Retrieval-First Routing: No generation occurs without prior successful retrieval.
2. Deterministic Preprocessing: Structural problems (e.g., listing items) are solved at ingestion time via chunk consolidation, not at query time via prompting.
3. Offline-First Operation: Essential services (Vector search, STT, TTS) run locally to ensure kiosk responsiveness.
4. Structural Fixes over Prompt Tuning: We prioritize fixing data quality (chunking strategies, normalization) over complex prompt engineering.

Scope and Limitations
The current system is scoped to "Informational" and "Wayfinding" tasks. It does not perform transactional operations (e.g., enrolling students, paying fees) or personalized data access (e.g., "what are *my* grades"). It is limited by the freshness of the uploaded documents and the quality of the STT transcription in noisy environments. While the knowledge base is dynamic, the entity extraction rules for new types of data currently require code configuration rather than being fully self-learning.
