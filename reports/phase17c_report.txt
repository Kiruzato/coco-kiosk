Phase 17C: Single Retrieval Pipeline + Enumeration Stability
=============================================================
Date: 2026-01-27
Project: CoCo - Campus RAG Chatbot

PROBLEM
-------
1. Dual retrieval: ConversationalRetrievalChain performed a SECOND vector search
   with a potentially reformulated query, so the LLM received different chunks
   than the ones that were hybrid-ranked and grounding-validated.
2. RETRIEVAL_TOP_K = 4 was too low to capture all 5 college deans spread across
   multiple chunks.
3. Chunk boundary splits: The dean list in the source PDF was split across
   chunk_id 394, 395, and 396. Chunk 395 listed 3 deans (Capili, Matriano, Yap)
   and chunk 396 continued with 2 more (Gonzales, Gutierrez). No single chunk
   contained all 5.
4. Result: "list all the deans" returned 2-3 deans inconsistently.

SOLUTION OVERVIEW
-----------------
1. Eliminated dual retrieval (single pipeline).
2. Increased RETRIEVAL_TOP_K from 4 to 8.
3. Added hybrid score filtering to remove noise chunks before LLM context.
4. Added adjacent chunk expansion (+-1 merge) to heal split lists.
5. Enhanced LLM system prompt for enumeration thoroughness.

FILES CHANGED
-------------
1. campus_rag_chatbot/app.py        (main changes)
2. campus_rag_chatbot/retrieval_validator.py  (stopwords + keyword regex fix)

DETAILED CHANGES
----------------

=== campus_rag_chatbot/app.py ===

A) RETRIEVAL_TOP_K (line ~90)
   Before: RETRIEVAL_TOP_K = 4
   After:  RETRIEVAL_TOP_K = 8
   Reason: 5 deans across multiple chunks need more than 4 retrieval slots.

B) Eliminated ConversationalRetrievalChain in handle_campus_query() (lines ~944-994)
   Before:
     - Built a ConversationalRetrievalChain with its own retriever
     - Chain performed a SECOND vector search internally
     - LLM received chunks from the second search, not the validated ones
   After:
     - Build context string from already hybrid-ranked, validated retrieved_docs
     - Get conversation history from memory buffer
     - Construct system prompt with context + history + rules
     - Call llm.invoke() directly with SystemMessage + HumanMessage
     - Manually save to memory: memory.save_context({"question": query}, {"answer": answer})
     - Extract sources from the same retrieved_docs (no second retrieval)

C) Eliminated ConversationalRetrievalChain in handle_directory_query() (line ~1533)
   Same pattern as (B) for the directory RAG fallback path.

D) Import changes (top of file)
   Added:   from langchain_core.messages import SystemMessage, HumanMessage
   Removed: ConversationalRetrievalChain (no longer used anywhere)

E) New helper: _expand_with_adjacent_chunks() (lines ~803-870)
   Purpose: Heal chunk boundary splits by merging +-1 neighbors inline.
   How it works:
     - For each retrieved chunk, find chunk_id-1 and chunk_id+1 in the vector
       store docstore (if not already in the retrieved set).
     - Merge neighbor content INTO the source chunk's page_content (prepend -1,
       append +1), preserving the same number of context blocks.
     - Example: chunk 395 ("deans: Matriano, Yap") gets chunk 394 prepended
       (clearer Capili mention) and chunk 396 appended (Gonzales, Gutierrez).
       The LLM now sees one merged block with all 5 deans.
   Performance: Iterates the FAISS docstore index once per query to find
   neighbors. This is fast (in-memory dictionary lookup, ~418 entries).

F) New helper: _build_annotated_context() (lines ~872-885)
   Purpose: Build LLM context string from retrieved docs.
   Simply joins doc.page_content with double newlines. Keeps hybrid-ranked
   order so most relevant chunks appear first.

G) Hybrid score filter (lines ~1009-1016)
   After hybrid re-ranking, only chunks with hybrid_score >= 0.6 pass to the
   LLM. This filters out noise chunks that don't contain query keywords
   (their hybrid scores are ~0.49 due to 0.0 keyword component). Chunks with
   keyword matches score ~0.79+ and easily pass.
   Fallback: if filtering removes ALL chunks, use unfiltered results.

H) Enhanced LLM system prompt (lines ~960-968)
   Added rule 6: "When listing or enumerating items, scan ALL provided context
   thoroughly and include every person/item that holds the requested role.
   A person may be identified by their title appearing near their name."
   This instructs the LLM to look across all context blocks for enumeration
   queries instead of stopping at the first list it finds.

I) Logging additions
   - "[PHASE17C] After hybrid filter: N chunks (from M)" - shows filter effect
   - "[PHASE17C] Expanded N chunks with +-1 neighbors" - shows expansion
   - "[PHASE17C] Built context from N chunks" - final context block count
   - "[PHASE17C] Passing N validated chunks to LLM" - what the LLM receives

=== campus_rag_chatbot/retrieval_validator.py ===

A) STOPWORDS expanded (line ~48-49)
   Added: 'list', 'show', 'give', 'name', 'all', 'every', 'each'
   Reason: These are command/enumeration words, not subject terms. Without
   filtering them, "list all the deans" extracted terms ['list', 'all', 'deans']
   which diluted keyword scores (chunks don't contain "list" or "all"), dragging
   hybrid scores below MEDIUM confidence and misrouting to general mode.

B) Keyword scoring regex fix (lines ~174-177)
   Before: pattern = r'\b' + re.escape(term) + r's?\b'
   After:  stem = term.rstrip('s') if term.endswith('s') and len(term) > 3 else term
           pattern = r'\b' + re.escape(stem) + r's?\b'
   Reason: Query term "deans" (plural) didn't match chunks containing "dean"
   (singular). Now "deans" is stemmed to "dean" before regex matching, so
   "dean" and "deans" both match.

RETRIEVAL PIPELINE FLOW (AFTER)
-------------------------------
Query
  -> Normalize text
  -> FAISS vector search (k=8, threshold=0.5)
  -> Extract query terms (stopword-filtered)
  -> Compute keyword scores (coverage + frequency)
  -> Combine hybrid scores (0.7 * vector + 0.3 * keyword)
  -> Re-rank by hybrid score
  -> Validate grounding (query terms in top chunks)
  -> Filter: keep only chunks with hybrid_score >= 0.6
  -> Expand: merge +-1 neighbors into each chunk
  -> Build context string (hybrid-ranked order)
  -> Direct LLM call with SystemMessage + HumanMessage
  -> Save to conversation memory
  -> Build structured answer + sources from same chunks

ROOT CAUSE ANALYSIS
-------------------
The core issue was a CHUNK BOUNDARY SPLIT in the source PDF. The student manual
review committee section lists deans across two consecutive chunks:

  Chunk 394: "...dr. leilani e. capili & faculty dean, college of nursing..."
  Chunk 395: "...deans: dr. eric a. matriano, engr. noel h. yap..."
  Chunk 396: "...arch. corazon z. gonzales, dr. engr. vivian e. gutierrez..."

No single chunk contains all 5 deans. The fixes address this at multiple levels:
1. Higher k (8 vs 4) retrieves more chunks covering the split
2. Adjacent expansion merges chunks 394+395+396 into one context block
3. Hybrid score filter removes noise chunks that confuse the LLM
4. Enhanced prompt ensures the LLM scans all context for enumeration

ARCHITECTURE NOTES FOR FUTURE WORK
-----------------------------------
- The adjacent chunk expansion iterates the full FAISS docstore (~418 docs).
  This is O(N) per query but fast in practice (in-memory). If the document
  count grows significantly, consider building a chunk_id index.
- The MIN_HYBRID_SCORE_FOR_CONTEXT = 0.6 threshold works because keyword-matched
  chunks score ~0.79+ and non-matched score ~0.49. If hybrid weights change,
  this threshold may need adjustment.
- The +-1 expansion assumes sequential chunk_ids from the same document are
  continuous text. This holds for the current chunking strategy (RecursiveCharacterTextSplitter).
