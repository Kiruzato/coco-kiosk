Iteration 1:
This iteration built the basic architecture for the Retrieval-Augmented Generation (RAG) system. The goal was to prove that a localized pipeline could answer questions using campus documents. We built the core ingestion workflow, vector storage, and a generation loop using a Large Language Model (LLM). This demonstrated that the concept was feasible for an informational kiosk.

Iteration 2:
We addressed the problem of model hallucination to ensure reliable answers. To make the system trustworthy, we added a verification layer. This iteration introduced "grounding" checks to confirm that answers were supported by retrieved text, along with a confidence scoring system. These features turned the prototype into a deterministic tool that rejects questions when it cannot find sufficient evidence.

Iteration 3:
This iteration defined what questions the system should answer. We needed to limit the model to campus-specific topics rather than general knowledge. A classification layer was built to distinguish between "in-domain" campus queries and general inquiries. This ensured the system functioned as a specialized assistant for school policy and wayfinding, not a generic chatbot.

Iteration 4:
We focused on making the system maintainable for the long term. Non-technical staff needed to update the knowledge base without help from engineers. We built a document management interface that allows administrators to upload, delete, and re-index documents. This functionality was essential for deploying the system in a production environment.

Iteration 5:
This phase solved precision problems with location-based queries. Standard RAG methods were often too variable for strict directory questions. We adopted a hybrid approach by adding a structured entity registry alongside the vector search. This allowed the system to accurately resolve queries about specific buildings and offices, eliminating errors in critical wayfinding tasks.

Iteration 6:
We moved the system from a stateless model to a conversational one. Users often ask follow-up questions that depend on previous context. We added a memory module to track conversation history. This allowed the system to understand references to earlier turns, making interactions feel more natural and useful.

Iteration 7:
This iteration improved how the system handles vague queries. Usage data showed that users often provide incomplete information. We implemented a disambiguation framework that detects multiple potential matches and asks the user for clarification. We also added logic to detect when a user changes the topic, ensuring the context updates correctly.

Iteration 8:
We shifted focus to optimization using data. To diagnose failures and measure performance, we built a comprehensive observability layer. This infrastructure logs events and tracks analytics, giving us detailed data on query patterns and refusal rates. This data provided the evidence needed to refine our algorithms.

Iteration 9:
We overhauled the architecture to address failures in vector-based search. Vector embeddings sometimes missed exact keyword matches. To fix this, we implemented a "Hybrid Retrieval" method. This combined vector similarity with keyword scoring (BM25) and enforced a strict "retrieval-first" rule. This ensured the model only used validated, relevant text, which improved how well it found specific campus terms.

Iteration 10:
This phase focused on extracting lists reliably from text. The system initially struggled to retrieve complete lists (like all faculty deans) because the information was fragmented. We introduced "Entity-Centric Consolidation," which pre-groups related entities into single text chunks. Combined with a text normalization pipeline, this ensured that list-based answers were complete and consistent.

Iteration 11:
We addressed difficulties in retrieving long narratives, such as policies or prayers. Previous keyword rules were too strict for this type of content. We introduced "Semantic Grounding" to allow high-quality semantic matches to pass validation even without exact keywords. We also added a mechanism to stitch adjacent text chunks together, preserving the flow of long documents.

Iteration 12:
This iteration focused on scalability and code health. As the system grew, the logic became complex. We refactored the consolidation tools into a generic configuration-driven engine. We also added a metadata index to allow fast O(1) lookups. These improvements reduced technical debt and made the retrieval pipeline more efficient for larger datasets.

Iteration 13:
We targeted state-of-the-art retrieval quality. We replaced our linear scoring capability with Reciprocal Rank Fusion (RRF), a standard method for combining search results. We also added query expansion using synonyms and filters to ensure diverse results. These changes helped the system handle different user vocabularies and provided a broader set of search results.

Iteration 14:
We used our established patterns to add new capabilities. We built specific extractors for event dates and office contact information. By processing these data types with specialized pipelines, the system achieved high precision for schedule and contact queries, reducing the chance of hallucination for factual data.

Iteration 15:
The final step introduced a voice interface. We integrated an offline-first "Voice Modality Layer" using Speech-to-Text (STT) and Text-to-Speech (TTS) services. This required an orchestration layer to manage timing and state. This transformed the text-based engine into a full voice assistant suitable for a physical kiosk.
