OVERVIEW
================================================================================

Phase 7 introduces a web-based Admin Document Management System (DMS) that
allows authorized administrators to remotely manage the chatbot's knowledge
base from any PC on the same WiFi network.

KEY CAPABILITIES:
1. Upload documents (PDF, DOCX, TXT) via web interface
2. View all ingested documents with metadata
3. Delete documents from vector store and disk
4. Secure API key authentication
5. Real-time updates and notifications
6. No installation required on admin PC - browser-based access

ARCHITECTURE:
- Single source of truth: Raspberry Pi 5
- LAN-only access via HTTP (WiFi network)
- Browser-based UI (no client installation needed)
- RESTful API with authentication
- Automatic vector store updates on upload/delete

HOW THE SYSTEM WORKS
================================================================================

ARCHITECTURE FLOW:
-----------------

1. ADMIN ACCESS FROM REMOTE PC
   ┌──────────────────────────────────────────────────────────────────┐
   │ Admin PC on WiFi                                                 │
   │ ┌────────────────────────────────────────────────────────────┐   │
   │ │ Browser: http://[Pi-IP]:8000/admin                         │   │
   │ │ 1. Loads admin.html, admin.js, admin.css from Pi           │   │
   │ │ 2. User enters API key                                      │   │
   │ │ 3. JavaScript stores key in sessionStorage                  │   │
   │ │ 4. All API calls include X-API-Key header                   │   │
   │ └────────────────────────────────────────────────────────────┘   │
   └──────────────────────────────────────────────────────────────────┘
                                    ↓ HTTP Requests
   ┌──────────────────────────────────────────────────────────────────┐
   │ Raspberry Pi 5 - FastAPI Server (0.0.0.0:8000)                   │
   │ ┌────────────────────────────────────────────────────────────┐   │
   │ │ verify_admin_api_key() dependency                          │   │
   │ │ - Checks X-API-Key header                                   │   │
   │ │ - Returns 401 if missing/invalid                            │   │
   │ └────────────────────────────────────────────────────────────┘   │
   │                             ↓ Authorized                         │
   │ ┌────────────────────────────────────────────────────────────┐   │
   │ │ Admin Endpoints: /admin/upload, /admin/documents, etc.     │   │
   │ └────────────────────────────────────────────────────────────┘   │
   │                             ↓                                    │
   │ ┌────────────────────────────────────────────────────────────┐   │
   │ │ DocumentManager (document_manager.py)                      │   │
   │ │ - ingest_document() - Add to vector store                  │   │
   │ │ - list_documents() - Get all metadata                      │   │
   │ │ - delete_document() - Remove and rebuild                   │   │
   │ └────────────────────────────────────────────────────────────┘   │
   │                             ↓                                    │
   │ ┌────────────────────────────────────────────────────────────┐   │
   │ │ Storage                                                     │   │
   │ │ - data/uploaded/ - Physical files                          │   │
   │ │ - vector_store/ - FAISS index                              │   │
   │ │ - document_registry.json - Metadata                        │   │
   │ └────────────────────────────────────────────────────────────┘   │
   └──────────────────────────────────────────────────────────────────┘

2. DOCUMENT UPLOAD FLOW
   --------------------
   Step 1: User selects file in browser
   Step 2: JavaScript creates FormData with file
   Step 3: POST /admin/upload with X-API-Key header
   Step 4: FastAPI validates authentication
   Step 5: Validate file extension (.pdf, .docx, .txt)
   Step 6: Save file to data/uploaded/[filename]
   Step 7: Call doc_manager.ingest_document(file_path)
   Step 8: DocumentManager:
           - Calculates file hash (duplicate detection)
           - Loads document content (format-specific loader)
           - Chunks text (500 chars, 50 overlap)
           - Generates embeddings via OpenAI API
           - Adds to FAISS vector store
           - Updates document_registry.json
   Step 9: Return document metadata to browser
   Step 10: JavaScript refreshes document table
   Step 11: Show success notification

3. DOCUMENT DELETE FLOW
   ---------------------
   Step 1: User clicks Delete button
   Step 2: JavaScript shows confirmation dialog
   Step 3: DELETE /admin/documents/{id} with X-API-Key
   Step 4: FastAPI validates authentication
   Step 5: Get document metadata from registry
   Step 6: Call doc_manager.delete_document(id)
   Step 7: DocumentManager:
           - Removes from document_registry.json
           - Rebuilds entire vector store (FAISS limitation)
           - Re-ingests all remaining documents
   Step 8: Delete physical file from data/uploaded/
   Step 9: Return success response
   Step 10: JavaScript refreshes document table
   Step 11: Show success notification

4. AUTHENTICATION MECHANISM
   -------------------------
   API Key Storage:
   - Server: Environment variable ADMIN_API_KEY in .env file
   - Client: sessionStorage (cleared when browser tab closes)

   Request Flow:
   1. Browser sends request with header: X-API-Key: [key]
   2. FastAPI Depends(verify_admin_api_key) executes
   3. Extracts x_api_key from Header
   4. Compares with ADMIN_API_KEY
   5. If match: Proceed to endpoint
   6. If no match: Return 401 Unauthorized

   Security Features:
   - API key not logged or exposed
   - sessionStorage (not localStorage) for auto-clear
   - LAN-only access (not exposed to internet)
   - Static key (suitable for single admin)

================================================================================
SECURITY ANALYSIS
================================================================================

1. AUTHENTICATION
   --------------
   Method: Static API key
   Strength: Moderate (suitable for LAN, single admin)

   Strengths:
   ✓ Simple to implement
   ✓ No user management needed
   ✓ Sufficient for trusted LAN environment
   ✓ Key stored securely on server (environment variable)

   Weaknesses:
   ⚠ Single key for all admins
   ⚠ No key rotation mechanism
   ⚠ No rate limiting
   ⚠ No session management

   Recommendations:
   - Change key periodically
   - Use strong, random UUID
   - Keep .env file secure (not committed to git)
   - Consider adding rate limiting for production

2. NETWORK SECURITY
   ----------------
   Protocol: HTTP (not HTTPS)
   Scope: LAN only

   Current State:
   ✓ Server binds to 0.0.0.0 (LAN accessible)
   ✓ CORS enabled for all origins
   ✓ No internet exposure (local network only)

   Risks:
   ⚠ HTTP transmits API key in plaintext (LAN only - acceptable)
   ⚠ Any device on WiFi can attempt access
   ⚠ No encryption of traffic

   Recommendations:
   - Do NOT expose to internet
   - Use WPA2/WPA3 encrypted WiFi
   - Consider HTTPS for production (self-signed cert acceptable)
   - Monitor server access logs

3. FILE UPLOAD SECURITY
   --------------------
   Validation:
   ✓ File extension whitelist (.pdf, .docx, .txt)
   ✓ File size limit (FastAPI default: 10MB)
   ✓ Files saved to dedicated directory (data/uploaded/)

   Risks:
   ⚠ No MIME type validation (could upload .exe renamed to .txt)
   ⚠ No virus scanning
   ⚠ No file content validation
   ⚠ Filename taken as-is (potential path traversal)

   Mitigations in Place:
   ✓ Python Path library prevents path traversal (auto-normalizes)
   ✓ Files stored in dedicated directory
   ✓ DocumentManager validates file format on ingestion

   Recommendations:
   - Add MIME type validation
   - Sanitize filenames (remove special characters)
   - Consider virus scanning for production

4. API KEY STORAGE
   ---------------
   Server Side:
   ✓ Environment variable (.env file)
   ✓ Not logged
   ✓ Not exposed in responses
   ✓ .env excluded from git (.gitignore)

   Client Side:
   ✓ sessionStorage (cleared on tab close)
   ✗ Not localStorage (persistent - security risk)
   ✓ Not visible in URL
   ✓ Transmitted in header (not query param)

   Best Practice:
   - Key cleared when browser tab closes
   - User must re-enter on new session
   - Reduces exposure window

================================================================================
KNOWN LIMITATIONS
================================================================================

1. FAISS DELETE PERFORMANCE
   ------------------------
   Issue: FAISS doesn't support incremental deletion
   Impact: Full vector store rebuild on every delete
   Workaround: Implemented, but slow for large document sets
   Alternative: Consider ChromaDB or Weaviate for production

2. NO PAGINATION
   -------------
   Issue: Document list loads all documents at once
   Impact: Slow UI with 100+ documents
   Workaround: Suitable for small deployments (<100 docs)
   Alternative: Add pagination in future phase

3. NO BACKGROUND JOBS
   ------------------
   Issue: Upload/delete blocks request until complete
   Impact: Browser waits during long operations
   Workaround: UI shows "Processing..." state
   Alternative: Implement Celery or RQ for background tasks

4. SINGLE ADMIN KEY
   ----------------
   Issue: One key for all admins, no user tracking
   Impact: Can't identify who uploaded/deleted documents
   Workaround: Acceptable for single admin
   Alternative: Implement user authentication in future

5. NO HTTPS
   --------
   Issue: Traffic not encrypted
   Impact: API key visible on network (LAN only)
   Workaround: LAN-only deployment, trusted network
   Alternative: Add self-signed certificate for production

6. NO DOCUMENT PREVIEW
   -------------------
   Issue: Can't preview document content before delete
   Impact: Must rely on filename and metadata
   Workaround: Careful review before deletion
   Alternative: Add preview modal in future
