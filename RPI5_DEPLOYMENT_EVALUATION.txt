                              EXECUTIVE SUMMARY
================================================================================

CONCLUSION: CONDITIONAL GO

The CoCo RAG chatbot system CAN be deployed on Raspberry Pi 5, but with
specific constraints and preparation requirements. The system is designed
with RPi5 deployment in mind (offline-first voice, ARM64-optimized models),
but critical operational decisions must be made regarding:

1. Document ingestion location (recommended: off-device pre-ingestion)
2. RAM configuration (8GB model strongly recommended)
3. Network connectivity (required for OpenAI API)
4. Storage type (SSD strongly recommended over SD card)

Key Findings:
- Runtime operation: FEASIBLE with 8GB RAM
- Voice processing: FEASIBLE with expected latency
- PDF ingestion: PROBLEMATIC on-device, recommend off-device
- Web server: FEASIBLE for kiosk (single-user) deployment

================================================================================
                          SUBSYSTEM EVALUATION
================================================================================

1. RAG PIPELINE
---------------

Status: FULLY COMPATIBLE

Components:
- FAISS similarity search: Native ARM64 support, O(ms) query time
- OpenAI embeddings: API call, network dependent (~100-300ms)
- OpenAI LLM (gpt-3.5-turbo): API call, network dependent (~500-2000ms)
- Hybrid retrieval (BM25+vector): Pure Python, negligible overhead

Bottleneck: Network latency to OpenAI API
Mitigation: Stable network connection required

Performance Expectation:
- Query latency: 1-3 seconds (dominated by OpenAI API)
- Embedding call: ~100-300ms
- LLM response: ~500-2000ms depending on response length

2. VECTOR STORE (FAISS)
-----------------------

Status: FULLY COMPATIBLE

Current State:
- 749 chunks indexed
- index.faiss: 4.6 MB
- index.pkl: 450 KB
- Embedding dimension: 1536 (OpenAI ada-002)

Scaling Estimate:
- 1,000 chunks: ~6 MB
- 5,000 chunks: ~30 MB
- 10,000 chunks: ~60 MB

On RPi5, FAISS similarity search is O(ms) even for 10K+ vectors.
Memory footprint scales linearly with chunk count.

3. PDF INGESTION (unstructured[pdf])
------------------------------------

Status: PROBLEMATIC - RECOMMEND OFF-DEVICE

The unstructured library with PDF support has significant resource demands:

Dependencies:
- pdfminer-six
- pdf2image (requires poppler)
- pillow
- opencv (optional but common)
- detectron2 (if using hi_res strategy)

Resource Impact (2.4 MB PDF, 749 chunks):
- RAM peak: 2-3 GB during parsing
- CPU: 100% all 4 cores for 2-5 minutes
- Disk I/O: Significant temp file creation

CRITICAL ISSUE:
On a 4GB RPi5, PDF ingestion will likely fail due to OOM.
On an 8GB RPi5, ingestion is possible but slow (5-10+ minutes).

RECOMMENDATION:
Pre-ingest documents on a development machine:
1. Run document_manager.py on desktop/laptop
2. Copy vector_store/ directory to RPi5
3. Copy document_registry.json to RPi5
4. Use RPi5 for runtime queries only

Alternative (simpler PDF fallback):
The system includes a pypdf fallback for linear extraction.
This uses less RAM but loses layout-aware parsing benefits.

4. VOICE - SPEECH-TO-TEXT (Whisper.cpp)
---------------------------------------

Status: COMPATIBLE WITH LATENCY

Model: ggml-tiny.en.bin (77 MB)
Engine: pywhispercpp (Python bindings to whisper.cpp)

Configuration (from config.py):
- Threads: 4 (matches RPi5 core count)
- Beam size: 5
- Language: English only (tiny.en)

Expected Performance on RPi5:
- 5 second audio: ~8-12 seconds processing
- 10 second audio: ~15-20 seconds processing
- 30 second audio: ~45-60 seconds processing

Real-time factor: ~1.5-2.0x (audio takes 1.5-2x its duration to transcribe)

This is acceptable for kiosk use where user waits for response.
NOT suitable for real-time streaming transcription.

Optimizations Applied:
- ARM NEON SIMD in whisper.cpp
- English-only model (faster than multilingual)
- 4-thread utilization

5. VOICE - TEXT-TO-SPEECH (Piper)
---------------------------------

Status: COMPATIBLE

Primary: Piper TTS (en_US-amy-medium, 63 MB ONNX model)
Fallback: edge-tts (Microsoft cloud, requires network)

Expected Performance on RPi5:
- Short response (50 words): 1-2 seconds
- Medium response (100 words): 2-4 seconds
- Long response (200 words): 4-8 seconds

Real-time factor: ~0.3-0.5x (faster than audio duration)

Piper uses ONNX Runtime with ARM64 optimizations.
The medium quality voice provides good naturalness without excessive latency.

6. WEB SERVER (FastAPI + Uvicorn)
---------------------------------

Status: FULLY COMPATIBLE

Configuration:
- Single worker (default)
- Host: 0.0.0.0:8000
- WebSocket support enabled

For kiosk (single-user) deployment:
- Single worker is adequate
- Concurrent requests not expected

Rate Limits (per client):
- transcribe: 30/minute
- synthesize: 60/minute
- chat: 20/minute

These limits are reasonable for kiosk use and protect against abuse.

7. ADMIN UI
-----------

Status: FULLY COMPATIBLE

The admin UI is static HTML/CSS/JS served by FastAPI.
No special server-side rendering.
All admin operations are API calls.

Browser Compatibility:
- Chrome/Chromium recommended for kiosk
- Firefox, Edge also supported

================================================================================
                          RISKS AND MITIGATIONS
================================================================================

1. NETWORK DEPENDENCY (HIGH RISK)
---------------------------------

Issue: OpenAI API required for embeddings and LLM
Impact: No network = no answers (even with cached vectors)

Mitigations:
- Ensure stable network (wired Ethernet preferred)
- Consider UPS for network equipment
- Implement graceful degradation (show "service unavailable")
- Future: Explore local LLM (Llama.cpp) for offline operation

2. MEMORY PRESSURE (MEDIUM RISK)
--------------------------------

Issue: 4GB RPi5 may OOM during voice + query
Impact: Process crash, service interruption

Mitigations:
- Use 8GB RPi5 model
- Configure swap (2-4GB on SSD, NOT SD card)
- Disable voice if memory is critical
- Monitor with systemd or watchdog for restart

3. SD CARD WEAR (MEDIUM RISK)
-----------------------------

Issue: Frequent writes degrade SD card
Impact: Data corruption, system failure

Mitigations:
- Use NVMe SSD via HAT
- Mount /tmp and logs as tmpfs
- Minimize logging verbosity in production
- Regular backups of vector_store/

4. THERMAL THROTTLING (LOW-MEDIUM RISK)
---------------------------------------

Issue: Sustained CPU load causes throttling
Impact: Increased latency, potential hangs

Mitigations:
- Active cooling (fan HAT or case)
- Monitor with vcgencmd measure_temp
- Adequate ventilation in kiosk enclosure

5. INGESTION FAILURE (MEDIUM RISK)
----------------------------------

Issue: PDF ingestion may fail on-device
Impact: Cannot update knowledge base

Mitigations:
- Pre-ingest on development machine
- Use simpler pypdf fallback (loses layout awareness)
- Copy pre-built vector_store to device

================================================================================
                      DEPLOYMENT RECOMMENDATIONS
================================================================================

1. HARDWARE SPECIFICATIONS
--------------------------

MINIMUM (text-only, pre-ingested):
- Raspberry Pi 5 4GB
- 32GB microSD (Class 10 A2)
- Stable network connection
- Passive cooling

RECOMMENDED (full voice):
- Raspberry Pi 5 8GB
- 64GB+ NVMe SSD (via HAT)
- Ethernet connection
- Active cooling (fan)
- UPS for power stability

2. SWAP CONFIGURATION
---------------------

For 4GB model: REQUIRED
For 8GB model: RECOMMENDED

# Create 4GB swap file on SSD (not SD card!)
sudo fallocate -l 4G /mnt/ssd/swapfile
sudo chmod 600 /mnt/ssd/swapfile
sudo mkswap /mnt/ssd/swapfile
sudo swapon /mnt/ssd/swapfile
# Add to /etc/fstab for persistence

3. INGESTION STRATEGY
---------------------

RECOMMENDED: Off-device pre-ingestion

Development Workflow:
1. Prepare documents on desktop/laptop
2. Run: python document_manager.py ingest <documents>
3. Verify: python app.py (test queries)
4. Copy to RPi5:
   - campus_rag_chatbot/vector_store/
   - campus_rag_chatbot/document_registry.json
   - campus_rag_chatbot/data/metadata_index.json
5. Start service on RPi5

This avoids the heavy unstructured library load on RPi5.

4. PRODUCTION DEPLOYMENT STRATEGY
---------------------------------

Option A: Systemd Service (Recommended)
- Create systemd unit file
- Auto-restart on failure
- Log rotation via journald
- Start on boot

Option B: Docker Container
- Containerized deployment
- Easier updates
- Higher memory overhead (~100-200 MB)

Sample systemd unit:

[Unit]
Description=CoCo Campus RAG Chatbot
After=network.target

[Service]
Type=simple
User=pi
WorkingDirectory=/home/pi/coco/campus_rag_chatbot
ExecStart=/home/pi/coco/venv/bin/python app.py
Restart=always
RestartSec=10
Environment=OPENAI_API_KEY=sk-...

[Install]
WantedBy=multi-user.target

5. MONITORING
-------------

Essential metrics to track:
- CPU temperature: vcgencmd measure_temp
- Memory usage: free -m
- Disk I/O: iostat
- Service uptime: systemctl status coco
- API latency: /voice/health endpoint

Consider setting up alerts for:
- Temperature > 80C
- Memory < 500MB free
- Service restart events

- Cannot ingest large PDFs on-device efficiently
- Voice latency not suitable for real-time conversation

The offline-first voice design (Whisper.cpp + Piper) aligns with edge
deployment goals, while the OpenAI API dependency for embeddings/LLM
requires reliable network infrastructure.
